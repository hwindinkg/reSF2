# План порта reSF2 → 1:1 с оригиналом

Цель: движок, который загружает ассеты и ведёт себя байт-в-байт как
оригинальная мобильная версия Shadow Fight 2 (APK v1.9.21, Marmalade SDK +
Cocos2d-x 2.x). Приоритет источников: Marmalade (`ShadowFight2.s86` /
`ShadowFight2_android.bin`), затем Unity IL2CPP (`libil2cpp.so` v2.46).

## Правила работы

1. За один запуск закрывается **минимум один пункт целиком** — со сборкой,
   проверкой и коммитом. Полупункты не засчитываются.
2. Каждое изменение помечается `[ORIGINAL]` с адресом/символом бинарника либо
   `[HEURISTIC-TODO]`. Третьего не дано.
3. Никаких констант, подобранных на глаз, без явной пометки и объяснения, из
   какого измерения они получены.
4. Пункт считается закрытым только при наличии **проверки**: тест, скриншот
   против эталона или численное сличение с бинарником.

## Фаза 1 — Система координат и камера

- [x] **1.1 Единая система координат + инструментальная проверка.**
  Оверлей `--debug-world` (F1 переключает) рисует в мировых координатах оси,
  границы `Width`×`Height`, полосу масок, две независимые оценки плоскости
  пола, маркеры NPivot и самой нижней точки бойца, маркер противника — плюс
  числовой вывод. Реализация: `Game::render_debug_world()`.

  **Замеры на dojo (1280×720), первый запуск:**

  ```
  params  Width=1960 Height=560 Wall=305 Floor=80
  view    zoom=1.2857  visible 996 x 560 world units
  camera  x=-380.9 y=0.0
  mask band  top=226 bottom=-220  height=446
  floor A (-H/2+Floor)=-200   B (layer_3 top)=-193  delta=7
  player  pivot=(-457, -75)  y_adjust=18.2  lowest node=-331
  player  foot-vs-floorA=-131  foot-vs-floorB=-138
  enemy   pos=(-305, -105)   params X=973 -> X-W/2=-7
  ```

  **Что это дало:**

  1. **Система координат подтверждена.** Две независимые оценки пола сходятся
     в пределах 7 единиц: `-Height/2 + Floor = -200` и верхняя кромка полосы
     `layer_3` = `-193`. Значит `Floor="80"` — это нижний отступ от границы
     мира, а модель «`<Image>` центрированы и Y-инвертированы» верна.
  2. **Настоящий баг найден и измерен: боец проваливается сквозь пол на
     131–138 единиц** (нижняя точка `-331` против пола `-193..-200`). Это не
     камера. Прежняя оценка «~87 единиц на глаз» была неверной — реальное
     расхождение в полтора раза больше.
  3. **Локализовано до данных анимации.** `resolve_body_node` считает
     `sy = world_cy + (ly - pivot_local_y)` при масштабе 1.0. Из
     `sy = -331`, `world_cy = -75`, `pivot_local_y = 169.48` следует
     `ly = -86.5` — то есть анимация даёт ступне **отрицательный** Y в
     model-space, хотя в покое `NToe ≈ 65.5`. В кадре анимации ступня
     оказывается на 256 единиц ниже пивота вместо 104 — ровно в 2.46 раза.
     Подозрение: разбор `.bin` (единицы/шаг) либо пропущенный масштаб.
  4. **Побочная находка:** `enemy_pos_x_ = -305`, хотя из params следует
     `973 - 980 = -7`. Значит позицию противника кто-то переписывает после
     инициализации. Отдельная задача, см. 5.3.
  5. Видимая полоса по маскам — 446 из 560. Судить о кадре нельзя, пока не
     починен пункт 3.1.

## Фаза 3 — Модель бойца

- [x] **3.1 Боец проваливался сквозь пол на 131–138 единиц.**
  Причина оказалась не в разборе `.bin` (данные там верные) и не в масштабе.

  **`.bin` авторены в floor-space: пол = y 0.** Координаты в файле абсолютные,
  из сцены авторинга (X ≈ −350). Правильное размещение:

  ```
  world_y = floor_world_y + absolute_animation_y      floor = -Height/2 + Floor
  world_x = player_x + (anim_x - anim_npivot_x)       X — относительно пивота
  ```

  Прежний код делал `world_cy + (ly - pivot_local_y)`, вычитая покоящийся
  пивот (169.48) из уже пивот-относительного значения, и пытался залатать это
  через `y_adjust` с клампом ±50, которого не хватало в разы.

  Замер по всем кадрам, нижняя точка бойца (пол = −200):

  | анимация | было | стало |
  |---|---|---|
  | `fists1_stance_idle` (38 кадров) | −102.8 | −201.3 .. −201.2 |
  | `stance_idle` (79) | −134.3 | −199.2 .. −199.1 |
  | `stance_2` (52) | −208.7 | −200.6 .. −194.0 |
  | `jump` (29) | −218.7 | −202.5 .. −4.0 |

  Дуга прыжка получилась бесплатно — она уже лежит в данных анимации.
  В рантайме оверлей показывает `foot-vs-floorA = 1`.

  Побочно: `PlayerPositionY` больше не участвует в вертикальном размещении
  анимированного бойца. Это верно (высоту задаёт анимация), но означает, что
  вертикальный сдвиг геймплеем — отбрасывание, нокдаун — пока применить
  некуда. Отдельным пунктом 5.2.

  `ShiftModelNode`, узел-якорь) и покрыт конформанс-проверками.

  **Не сделано и требует сверки с бинарником.** Текущая модель накапливает

  | анимация | дрейф NPivot | дрейф NHeel_2 | ShiftX |
  |---|---|---|---|
  | `stance_2` | −167.26 | −173.44 | 70 |
  | `stance_idle` | 0.00 | 0.00 | 0 |
  | `step_forward` | +66.00 | +66.00 | 0 |

  размещения. Вопрос к бинарнику: как оригинал сочетает выравнивание по
  якорю с продвижением при шаге (подозрение — смена опорной ноги

- [x] **5.2b Детектор попаданий считал конечности по старой сломанной формуле.**
  У детектора оказалась **своя копия** трансформа model-space → world-space:

  ```cpp
  limb_wy = player_pos_y + y_adjust + (limb_ly - pivot_ly);   // двойное вычитание
  ```

  Это ровно та формула, которую 3.1 заменил в `resolve_body_node`, но
  детектор её не разделял. Конечности проверялись на ~170 единиц ниже, чем
  рисовались: боец мог стоять вплотную к груше, бить — и не попадать.
  Третий случай подряд, когда дублирование логики прячет баг (после 8.4
  «гейт приоритета» и 5.2a «интервалы»).

  Теперь детектор вызывает `resolve_body_node` — общий код с рендером.
  Замер трассой (подойти к груше и ударить дважды): было `bag_hit` 0 раз,
  стало 2 раза на кадрах 369–370 внутри `high_punch`.

  **Осталось:** `bag_angle` по-прежнему 0, то есть сработал путь «попадание
  по противнику по дистанции», а не коллизия с самой грушей (тот путь и
  выставляет угол). Собственная коллизия груши — отдельный пункт 5.2c.

- [x] **5.2c Коллизия с грушей — три причины, все устранены.**
  Диагностика вместо догадок: `[BAG]` — мировая коробка груши, коллизионные
  рёбра, закреплённые узлы; `[ATK]` — самая дальняя точка бьющей конечности и
  зазор до груши; `[BAGSOLVE]` — счётчики решателя и худшее нарушение связи.

  1. **Узел `COM` в свободном падении.** Коробка уезжала до `y=-5768` при
     худшем нарушении связи `0.2` — верёвка цела, падало то, что вне связей.
     `COM` (центр масс) не физический и ни в одной связи не состоит.
     Узлы без связей теперь замораживаются.
  2. **Проверка по противнику съедала окно атаки.** Внешний гейт
     `if (in_attack_interval && !hit_this_interval_)` закрывался, как только
     срабатывала дистанционная проверка по противнику. В додзё противник и
     груша стоят в одной точке (`x=-7`), поэтому проверка по противнику
     выигрывала всегда, а тест груши не выполнялся на кадре максимального
     сближения. У противника есть свой `invuln_time`, флаг там не нужен.
  3. **Импульс.** После разбора интервалов (5.2a) `<Impulse X="245"/>`
     наконец доезжает до `MoveDef`; `apply_bag_impulse` делит его на массу
     (9.375) и сдвигает узел.

  Итог, замер одного прогона: попадание на игровом кадре 370, дальше
  `bag_move` (смещение узлов от покоя) идёт
  `1.3 → 43.8 → 106 → 152 → 195 → 202`, затем колебания затухают
  `39 → 69 → 23`. Груша получает удар, раскачивается и успокаивается.

  Мои прежние «0.06 единицы» были из прогона, где попадания просто **не
  случилось**: коллизия краевая (`sq_dist=267` против порога `361`), а число
  игровых кадров плавает от прогона к прогону. Отсюда же вывод — тест на
  попадание по груше будет нестабильным, пока не убран источник дрожания
  (см. 9.8).

- [x] **9.8 Прогон сделан детерминированным.**

  активном скрипте платформа уже игнорировала, так что Escape ни при чём.
  Настоящая причина — **потеря фокуса**: окно уходит в паузу, цикл крутит
  `sleep_ms(100)` без продвижения кадра, и внешний таймаут рубил прогон в
  случайный момент. Отсюда 0, 240, 472, 540 кадров при одинаковых аргументах.

  Две правки:
  * `GlfwPlatform::is_paused()` не ставит паузу, когда заряжен input-script —
    скриптованный прогон это измерение, оно не должно зависеть от того, что
    ещё на десктопе в фокусе;
  * фиксированный шаг `dt = 16` мс для скриптованных прогонов вместо
    настенных часов — иначе физика шагала по-разному и краевая коллизия
    попадала не в каждом прогоне.

  Результат: 618 кадров, 1 попадание, смещение груши `214.490` — совпадает
  до третьего знака в каждом прогоне.
