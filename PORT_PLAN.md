# План порта reSF2 → 1:1 с оригиналом

Цель: движок, который загружает ассеты и ведёт себя байт-в-байт как
оригинальная мобильная версия Shadow Fight 2 (APK v1.9.21, Marmalade SDK +
Cocos2d-x 2.x). Приоритет источников: Marmalade (`ShadowFight2.s86` /
`ShadowFight2_android.bin`), затем Unity IL2CPP (`libil2cpp.so` v2.46).

## Правила работы

1. За один запуск закрывается **минимум один пункт целиком** — со сборкой,
   проверкой и коммитом. Полупункты не засчитываются.
2. Каждое изменение помечается `[ORIGINAL]` с адресом/символом бинарника либо
   `[HEURISTIC-TODO]`. Третьего не дано.
3. Никаких констант, подобранных на глаз, без явной пометки и объяснения, из
   какого измерения они получены.
4. Пункт считается закрытым только при наличии **проверки**: тест, скриншот
   против эталона или численное сличение с бинарником.

  1. **Система координат подтверждена.** Две независимые оценки пола сходятся

     расхождение в полтора раза больше.

- [x] **2.2 `SimpleEffect` / `Transparency`.**
  Кривая отреверсена целиком и реализована.

  Ниточка: `Location::parseSimpleEffect` (`0x10145a90`) → `Curve::addPoint`
  (`0x1007f020`) → `Curve::recompute` (`0x1007f0c0`) → `Curve::advance`
  (`0x1007f680`) → `SimpleEffect::update` (`0x1007f1f0`).

  Оригинал гоняет через **один и тот же** тип кривой четыре канала:
  `Transparency`, `OscillationX`, `OscillationY`, `Rotation` (плюс `Speed`,
  `ReappearX/Y` — эти не кривые). Реализована пока прозрачность.

  **`<Point>` — это отрезок, а не ключевой кадр.** `Value` — значение в
  **начале** отрезка, `Period` — его длительность, а значение в конце берётся
  из **следующей** точки; последний отрезок замыкается на первую. То есть вся
  кривая — один цикл длиной в сумму периодов (для светового пятна dojo это
  9.2 с).

  `recompute` решает коэффициенты так, чтобы отрезок точно попадал в оба
  конца:

  ```
  P == 0 :  b = 0, c = 0
  E == 0 :  b = (V' - V) / P                      c = V
  иначе  :  b = ((V' - V) - P*P*E) / (2*E*P)      c = V - b*b*E
  ```

  а `update` вычисляет

  ```
  E == 0 :  value(t) = c + b*t                    (прямая)
  иначе  :  value(t) = c + E*(t + b)^2            (парабола)
  ```

  Подстановка даёт середину отрезка `V + (V'-V)/2 - E*P^2/4`, то есть
  **отклонение от прямой ровно `-E*P^2/4`** и от диапазона значений не
  зависит. При `P=2, E=±1` это всего одна единица из ста — моя первая версия
  теста требовала большего отклонения и падала на верном коде.

  Время — **в секундах**: `0x1007f1f0` умножает счётчик 60-герцовых тиков на
  1/60 прежде чем трогать кривую. `Offset` — не отдельный механизм, а
  однократный `advance(Offset)` после набора точек. Значения `Transparency`
  зажимаются в `[0, 100]` **при добавлении** (`0x1007e6c0`), то есть это
  проценты, и применяются как `setOpacity((int)(value * 2.55) & 0xff)`.

  **Проверка двумя уровнями.** `tests/test_effect_curve.cpp` (49 проверок) —
  математика: непрерывность на каждой границе отрезка для обеих ветвей,
  замыкание цикла, возврат в ту же фазу через полный период, игнор
  отрицательного шага, `Offset` как фаза, зажим процентов, закон `-E*P^2/4` на
  двух разных периодах, и настоящее пятно dojo (4 точки, цикл 9.2 с,
  прогон всего цикла не выходит за 45..75%).

  Этого мало: тест доказывает формулу, но не то, что движок её **крутит**.
  Поэтому в `[STATE]` добавлено `fx=` — альфа первого анимированного эффекта,
  и `test_input_trace` требует, чтобы за прогон она реально менялась. Замер:
  `45.5% .. 75.0%`. Без этого замороженная кривая прошла бы обе проверки:
  пятно `layer_4` при стартовом положении камеры находится **за кадром**, так
  что на экране такой дефект не виден.

  **Осталось:** `OscillationX/Y` и `Rotation` — тот же тип кривой, но они
  двигают узел, а не красят его, поэтому требуют, чтобы эффект был узлом сцены.

## Фаза 3 — Модель бойца

- [x] **3.1 Боец проваливался сквозь пол на 131–138 единиц.**
  Причина оказалась не в разборе `.bin` (данные там верные) и не в масштабе.

  **`.bin` авторены в floor-space: пол = y 0.** Координаты в файле абсолютные,
  из сцены авторинга (X ≈ −350). Правильное размещение:

  ```
  world_y = floor_world_y + absolute_animation_y      floor = -Height/2 + Floor
  world_x = player_x + (anim_x - anim_npivot_x)       X — относительно пивота
  ```

  Прежний код делал `world_cy + (ly - pivot_local_y)`, вычитая покоящийся
  пивот (169.48) из уже пивот-относительного значения, и пытался залатать это
  через `y_adjust` с клампом ±50, которого не хватало в разы.

  Замер по всем кадрам, нижняя точка бойца (пол = −200):

  | анимация | было | стало |
  |---|---|---|
  | `fists1_stance_idle` (38 кадров) | −102.8 | −201.3 .. −201.2 |
  | `stance_idle` (79) | −134.3 | −199.2 .. −199.1 |
  | `stance_2` (52) | −208.7 | −200.6 .. −194.0 |
  | `jump` (29) | −218.7 | −202.5 .. −4.0 |

  Дуга прыжка получилась бесплатно — она уже лежит в данных анимации.
  В рантайме оверлей показывает `foot-vs-floorA = 1`.

  Побочно: `PlayerPositionY` больше не участвует в вертикальном размещении
  анимированного бойца. Это верно (высоту задаёт анимация), но означает, что
  вертикальный сдвиг геймплеем — отбрасывание, нокдаун — пока применить
  некуда. Отдельным пунктом 5.2.

- [~] **4.3 Root motion — найдена настоящая модель оригинала: `<Align>`.**
  Каждый ход в `moves.xml` несёт блок выравнивания, который до сих пор
  разбирался лишь частично (узел-якорь читался, но **нигде не использовался**,
  как и интервалы до 5.2a):

  ```xml
  <Align Axis="X|Z" ShiftModelNode="NPivot">
    <Pivot Object="Nodes" Part="NHeel_2"/>
    <Position Player="Me" Object="Pivot" ShiftX="70"/>
  </Align>
  ```

  Смысл: названный узел **анимации** ставится в позицию бойца плюс сдвиг.
  Статистика по файлу: 774 хода объявляют `<Align>`, 717 называют якорь;
  718 выравниваются по `X|Z` и 51 по `X|Y|Z` — то есть вертикаль обычно
  берётся прямо из анимации, что сходится с находкой 3.1. Самые частые
  якоря — пятки: `NHeel_2` 437 раз, `NHeel_1` 176 (боевая анимация
  вращается вокруг опорной ноги). 74 хода анкерятся на узлы навесных
  моделей (`Magic-Node2_1` ×51, `Ranged-Node*_1` ×13, `MassBomb-MacroNode1`
  ×10) — их нет в `skeleton.xml`.

  **Потребитель найден в бинарнике, закон выписан целиком.** Ниточка:
  строка `"Model::getModelAlign aligned to Self instead of Enemy"`
  (`0x105b18e8`) → `Model::getModelAlign` (`0x10159700`) → разбор
  (`0x1017e140`) и применение.

  Раскладка `Align` внутри `MoveInfo` (база `Move+0x68`, разбор
  `MoveInfo::parseAlign` @ `0x1017e140`, значения enum сверены со строковой
  таблицей):

  | смещение | поле |
  |---|---|
  | `+0x68` | `Pivot Object`: 1 `Nodes` `0x105b25f8`, 2 `Wall` `0x105b028c`, 3 `Animation` `0x10379eb0`, 4 `Pivot` `0x105b3c40` |
  | `+0x6c` | `Position Object`, тот же enum |
  | `+0x70` / `+0x74` | индекс узла-якоря и его **зеркальный** индекс |
  | `+0x78` / `+0x7c` | то же для `Position` |
  | `+0x84/85/86` | флаги осей X / Y / Z |
  | `+0x88` / `+0x94` | `Pivot Part` / `Position Part` (std::string) |
  | `+0xa0` | `ShiftModelNode` |
  | `+0xac` / `+0xb0` | `Pivot Player` / `Position Player` |
  | `+0xb4` / `+0xb8` | `ShiftX` / `ShiftY` |
  | `+0xbc` | `has_align` |

  `ModelAnimation::playInfo` (`0x10164fa0`) при **старте** анимации выполняет
  по порядку: загрузка кадров → `mirrorNodes` (`0x10164c20`, подменяет
  индексы узлов на зеркальные, если модель развёрнута) →
  `setCurrentNode(align.pivotID)` (`0x10165c10`) → `alignAnimation`
  (`0x101661d0`). Выравнивание считается **один раз, не каждый кадр**.

  Сам закон (`0x101661d0`):

  ```
  pivot  = Pivot Object   Nodes     -> узел-якорь в ПЕРВОМ кадре новой анимации
                          Animation -> (0,0,0)
                          Wall      -> ±X стены локации
                          Pivot     -> текущий узел модели
  target = Position Object Pivot    -> текущий узел модели   (658 из 800)
                          Nodes     -> узел на выбранном игроке
                          Animation -> прошлое смещение модели
                          Wall      -> ±X стены
  target.x += facing * ShiftX          (0x10166403: MULSS на байт ±1)
  target.y += ShiftY                   (без множителя facing)
  offset  = target - pivot             (0x1028e890)
  offset  маскируется флагами <Align Axis>
  сдвинуть ВСЕ узлы на offset          (0x10166690)
  ```

  Ключевое звено — `setCurrentNode` (`0x10165c10`): он ставит «текущий узел»
  модели равным `align.pivotID` **новой** анимации, а позицию читает из модели,
  где ещё стоит **прежняя** поза. Значит `Position Object="Pivot"` означает:
  *узел-якорь остаётся там же, где он сейчас*, а тело переставляется вокруг
  него. Это и есть ответ на прежний вопрос — 613 из 800 блоков анкерятся на
  пятку, потому что боевая анимация вращается вокруг опорной ноги.

  А ход **без** `<Align>` даёт нулевое смещение: ctor `Align` (`0x10101c60`)
  оставляет оба enum-а `Object` равными 0 и все флаги осей сброшенными, так что
  `0x10166690` вызывается с (0,0,0). Все 91 таких хода — это
  `StepForward` / `StepBack` / `Shop*`: их перемещение целиком лежит в данных
  анимации. Отсюда прямое правило: **ходьбу переанкеривать нельзя, удары —
  нужно.** Прежнее подозрение «Align прибивает якорь, поэтому анимация бойца
  не двигает» было неверным: боец следует за анимацией всегда, Align задаёт
  лишь начальную привязку.

  **Реализовано** (`Game::apply_align`, вызывается из `play_animation`): случай
  `Pivot Object="Nodes"` + `Position Object="Pivot"` по оси X — 658 из 800
  блоков. В движке мировой X узла есть `player_pos_x + facing*(node_x -
  npivot_x)`, поэтому привязка якоря сводится к однократной поправке
  `player_pos_x`. Разбор дополнен: `Object` и `Part` теперь читаются и у
  `<Position>`, не только у `<Pivot>`.

  **Проверка.** В `[STATE]` добавлены `al=` и `anchor_x=` — мировой X узла-якоря
  (по `px` это не видно: `px` — это NPivot плюс смещение, а NPivot внутри
  анимации качается по замыслу, за вступительную стойку он проходит 167 единиц

- [x] **5.2c Коллизия с грушей — три причины, все устранены.**
  Диагностика вместо догадок: `[BAG]` — мировая коробка груши, коллизионные
  рёбра, закреплённые узлы; `[ATK]` — самая дальняя точка бьющей конечности и
  зазор до груши; `[BAGSOLVE]` — счётчики решателя и худшее нарушение связи.

  1. **Узел `COM` в свободном падении.** Коробка уезжала до `y=-5768` при
     худшем нарушении связи `0.2` — верёвка цела, падало то, что вне связей.
     `COM` (центр масс) не физический и ни в одной связи не состоит.
     Узлы без связей теперь замораживаются.
  2. **Проверка по противнику съедала окно атаки.** Внешний гейт
     `if (in_attack_interval && !hit_this_interval_)` закрывался, как только
     срабатывала дистанционная проверка по противнику. В додзё противник и
     груша стоят в одной точке (`x=-7`), поэтому проверка по противнику
     выигрывала всегда, а тест груши не выполнялся на кадре максимального
     сближения. У противника есть свой `invuln_time`, флаг там не нужен.
  3. **Импульс.** После разбора интервалов (5.2a) `<Impulse X="245"/>`
     наконец доезжает до `MoveDef`; `apply_bag_impulse` делит его на массу
     (9.375) и сдвигает узел.

  Итог, замер одного прогона: попадание на игровом кадре 370, дальше
  `bag_move` (смещение узлов от покоя) идёт
  `1.3 → 43.8 → 106 → 152 → 195 → 202`, затем колебания затухают
  `39 → 69 → 23`. Груша получает удар, раскачивается и успокаивается.

  Мои прежние «0.06 единицы» были из прогона, где попадания просто **не
  случилось**: коллизия краевая (`sq_dist=267` против порога `361`), а число
  игровых кадров плавает от прогона к прогону. Отсюда же вывод — тест на
  попадание по груше будет нестабильным, пока не убран источник дрожания
  (см. 9.8).

- [x] **9.8 Прогон сделан детерминированным.**
  Моя гипотеза в прошлый заход была **неверной**: реальную клавиатуру при
  активном скрипте платформа уже игнорировала, так что Escape ни при чём.
  Настоящая причина — **потеря фокуса**: окно уходит в паузу, цикл крутит
  `sleep_ms(100)` без продвижения кадра, и внешний таймаут рубил прогон в
  случайный момент. Отсюда 0, 240, 472, 540 кадров при одинаковых аргументах.

  Две правки:
  * `GlfwPlatform::is_paused()` не ставит паузу, когда заряжен input-script —
    скриптованный прогон это измерение, оно не должно зависеть от того, что
    ещё на десктопе в фокусе;
  * фиксированный шаг `dt = 16` мс для скриптованных прогонов вместо
    настенных часов — иначе физика шагала по-разному и краевая коллизия
    попадала не в каждом прогоне.

  Результат: 618 кадров, 1 попадание, смещение груши `214.490` — совпадает
  до третьего знака в каждом прогоне.

  | что | где |
  |---|---|
  | лист карты зоны | `assets/1536/image/zones/1..7.jpg` (1365×649) |
  | иконки узлов | `image/battles/{base,active,locked}/batchBattles*.plist` |
  | фото противника | `image/battles/<имя>.jpg` (484×274) |

  Координаты узлов — `<Battle X=".." Y="..">` из `stages.xml`, отсчёт **от
  центра листа**, Y вверх (в ZONE_1 турнир `Y=+10` стоит выше Рыси `Y=-45`,
  как на эталонном скриншоте). Диапазон по всем зонам: X −440..158,
  Y −220..145.

  Иконка узла — это **вид боя**, а не бой: атлас несёт по кадру на
  `tournament`, `survival`, `duel`, `training`, `challenge`, `final_battle`
  плюс по одному на каждого босса. Бои боссов зовутся `BOSS_<ИМЯ>` и имеют
  варианты `_INTERMISSION` / `_ECLIPSEMODE` / `_REPLAYABLE` того же узла,
  поэтому имя кадра — это имя без этой обвески в нижнем регистре. Для имён без
  своего кадра (`Bosses` в обучающей зоне) есть откат по `Type`.

  Подписи и заголовки берутся из локализации: `Tournament` → ТУРНИР,
  `characterLynx` → РЫСЬ, `ZONE_1` → «Перерождение», `startFight` → «В БОЙ!»,
  `stage` → «Стадия {0}/{1}».

  Собрано: лист зоны с горизонтальной прокруткой, узлы с иконками и
  подписями, боковой свиток (заголовок, фото противника, счётчик стадий с
  метками раундов, кнопка боя), верхняя панель и свиток «МЕНЮ» те же, что в
  додзё, внизу — название зоны и точки-страницы по числу зон.

  Свиток вынесен в `host_render_scroll_panel` — те же три куска
  (`Roll_*` 3-слайсом, пергамент, кромки `Paper_*`), что и диалог в додзё, так
  что каждый экран получает один и тот же свиток, а не свой цветной
  прямоугольник.

  **Побочно найдено: весь текст на экране задавался константами масштаба**
  (0.24, 0.28, 0.45, `fight_h/62`). Кегль растрового шрифта — 115 px при
  масштабе 1, так что «В БОЙ!» вышло вчетверо крупнее панели и уехало за
  экран. Введён `text_scale(px)`: запрашивается высота в пикселях от высоты
  кадра, как в HUD.

  Для проверки добавлен `--scene <имя>[:N]` — экран открывается напрямую,
  минуя Boot/Loading/меню (`--scene map:1` открывает карту на ZONE_1). Без
  этого сравнить экран с эталоном можно было только руками.

  **Осталось:** магазин, результаты, настройки; полоса сложности и цена входа
  в свитке; состояние `locked` у узлов (атлас есть, но правило открытия зон
  ещё не отреверсено — это 7.3).
